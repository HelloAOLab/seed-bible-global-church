ask-writings: where we are, where we are short

A brief for an outside planner. Date: 1 November 2026. It is written so a capable model or engineer who has never seen this system can propose a plan: what the agent does today, what the measurements say, how much of what we hold actually reaches an answer, and where the design is thin. Nothing here is a decision. The companion page ask-writings: measured, built, next records the work of the last two days.

What we want from you 1. Goal and constraints 2. The system today 3. Results 4. What the judge rewards 5. The ontology: held vs used 6. Skill artifacts 7. The plan: fixed, not built per question 8. Gaps, with evidence 9. Directions we see (not decided) 10. What you can use 11. Questions for you

What we want from you

A plan that makes our Scripture Agent's answers clearly better than Apologist's and Bonfire's on the Christian Ask questions (§3), without giving up what already makes ours different: every claim rests on held, verified text, and code — not a model — decides evidence, layers and dates. In particular we want your view on four things:

  1. Whether, and how, our ontology should drive answers (§5) — and what it lacks.
  2. Whether our skill artifacts should carry more than instructions (§6).
  3. Whether the plan should be constructed per question from typed steps, instead of one fixed pipeline (§7).
  4. What order to do it in, and how to tell each step worked (§10 lists the tests that exist).

1. Goal and constraints

Constraint (the owner's) What it rules out or requires
One harness — ask-writings — answers every kind of question No router to a second, simpler ask. A question type that does poorly is fixed inside the harness.
Models propose; code decides evidence, layers and dates Every claim names held evidence ids; a code check strikes the rest. A plan may be model-proposed but must be code-validated.
Haiku 5.5 is the model ($0.10 / $0.50 per million tokens) gpt-5-mini was tried inside the harness and did no better (§3). Larger models are a budgeted exception.
RunPod GPU time is a fixed cost; API calls are the metered spend Self-hosted models are welcome where they match; our 9B is not yet good enough to compose (§3.4).
Later readings are reception, never what a text says; a date is the date an item carries Layer discipline is a hard rule, checked by code.
The judge is Claude Haiku 5.5, blind to which system wrote an answer Numbers from different judges are never compared.

2. The system today

2.1 The steps (the same for every question)

Step Who What it does Median cost / time
classify Haiku, checked by code One of nine kinds (text, teach, history-of-reading, term, source, compare, verse, collection, edition) and anchors: verses (≤ 6, now including study-Bible cross-references), Strong's numbers, names, passages, three search phrasings. 16k input tokens · 1–3 s
gather code About fifteen channels in a few waves (§2.2). Verses through the signed corpus; writings citing the verse; parallels and scroll copies; the edition's own record; names and referents through the knowledge base; meaning search over 3.9M units; a question channel; cited-form and range resolution. 5–80 s
coverage + repair code Checks the pool against obligations generated from the kind; up to two targeted repair searches; a stop reason. 0–13 s
packet code + stock Qwen3-Reranker-0.6B Named passages first, ranked within soft per-layer preferences, filled to 90 items / 40k tokens. (In the eval harness; the deployed agent selects from the whole pool.) 3–10 s
select Haiku What the question asks (1–4 points), then an outline around them; every point names evidence ids. 30k tokens · 6–36 s
compose Haiku Answers each ask; names sources in the prose; lists every claim with its layer and evidence. 15k tokens · 17–36 s
check → revise → answer code (+ Haiku on revise) Strikes uncited claims, a "says" claim resting on a non-Scripture item, unheld quotations, dates no item carries, claims about the evidence itself; revises once (44% of answers). 16k tokens · ~23 s

An answer today: about 75k input and 10k output tokens, 4 model calls, about $0.013, and 50–90 s. Apologist and Bonfire answer in 12–19 s, without fetching or verifying anything.

3.3 The model is not the gap

Our harness run on gpt-5-mini scored no better than on Haiku 5.5 (addresses the question 0.64 vs 0.70; Scripture support 0.80 vs 0.92). The same gpt-5-mini inside Apologist scores 0.86 on addressing the question. The difference is the design — how the answer is planned and shaped — not the model.

3.4 Our own trained models

Our RunPod-trained Qwen3.5-9B translates at least as well as Haiku 5.5 (chrF3 44.4 vs 43.0 on 300 rows) but composes ask answers far worse on identical evidence (required-source recall 0.60 vs 0.81; layer discipline 0.62 vs 0.88).

4. What the judge rewards

For question-and-answer sets the judge reads the answer and the texts it cites (Scripture and writings, with their dates), compares it with the reference answer's claims (each with a role: required, supporting, optional), and returns:

  • intent — addressed / partly / no. Partly is typical when an answer engages the passage but does not give the reference's explanation, or hedges ("Scripture does not give a plain yes or no").
  • claims covered — stated / differs / contradicted / absent per reference claim.
  • scripture support — whether the cited passages carry what the answer claims.
  • restraint — fails on any unsupported additional claim, an overstatement or a material error. One stray date fails it.
  • strict good answer — every required claim stated, nothing contradicted, no major unsupported addition, support ≥ 0.8, intent addressed.

What the judge's reasons said about our answers (66 judged): 262 additional claims beyond the reference (mostly "defensible, minor" — padding); unsupported or wrong extras were mostly dates and remarks about the evidence ("dated AD 1567 by its work record", "these items are not used"); non-committal answers to doctrinal questions; and missing the central reading with its cross-references ("the cup is God's wrath", "the link to James 1:5").

5.2 What is used

  • Ontology channels supply 3% of cited evidence (§2.2).
  • Data-worker tools that exist but the ask never calls: graph_query, verse_dossier, get_chapter_interpretations, get_interpretation_index, find_entities, get_entity.
  • The 184 theological concepts are rules for translating a term (its rendering), not an account of what the doctrine teaches; they help a term question, not a catechism question.
  • Nothing in the ontology connects a doctrinal question ("what are the duties required in the seventh commandment?", "may true believers fall away?") to the propositions, proof texts and traditions' positions that answer it. On those questions we scored 0.00 on covering the reference.

6. Skill artifacts

Nine skills (skills/scripture/ask-*), one per question kind. Each is a short list of instructions plus shared evidence rules, and a declaration of the graph capabilities it may use. Example (ask-teach, added today): answer first; ground in Scripture with study-Bible cross-references; commit to the reading most Christians hold and name alternatives in a sentence; give a full list when a list is asked; no tangents; 150–250 words.

What the skills do not carry: worked examples of a good answer; the standard points an answer to a given question family must cover (e.g. a commandment question: what it requires, what it forbids, its scriptural ground, its reach to the heart); doctrinal scaffolds; per-tradition framing; question-specific retrieval plans; or tests that say a skill is working.

7. The plan: fixed, not built per question

Every question runs the same steps (§2.1). What varies with the classified kind is: the skill text the model reads; a static recipe per task (six tasks: explain-passage, author-or-tradition, compare-interpretations, trace-development, wording-or-witnesses, assess-prevalence) naming the layers the evidence must reach and which of three repair searches may run; and obligations generated from the anchors. Today's addition: select first writes what the question asks (1–4 points) and plans the outline around them.

Nothing constructs steps from the question. A doctrinal question, a history-of-reading question and "who is 'he' in verse 3" all gather through the same channels in the same waves; the recipe only changes which repairs are allowed.

8. Gaps, with evidence

  1. G1 Answer shape. Answers address the question less directly than the other apps (0.67 vs 0.86), pad (262 extra claims in 66), and hedge on doctrine. Partly fixed today (question-first planning, committed answers, no evidence remarks); measuring.
  2. G2 No doctrinal knowledge in the ask. Catechism and doctrine questions — a large share of the suite — have no source of structured doctrine: no propositions, no proof-text sets, no confessional positions. The ask reconstructs doctrine from verses each time (catechism coverage 0.00).
  3. G3 The ontology barely reaches the answer. 3% of cited evidence; the doctrine, interpretation and chronology contexts are not reachable; several graph tools are never called (§5).
  4. G4 The plan is static. One pipeline for every kind; no per-question construction of steps; channels run whether or not they serve the question (the evidence pool is ~100–300 items for a two-sentence question).
  5. G5 Skills are thin. Instructions only; no examples, no per-family coverage checklists, no tests.
  6. G6 Evaluation leakage. The Reformation Study Bible notes are held writings and are retrieved as evidence: 12 of 28 study-note answers cited the very note the reference was drawn from (claims covered 0.49 when they did, 0.35 when not). Schaff's Creeds of Christendom — the source of the catechism references — is held too. Our study-note scores are inflated until those sources are excluded when grading their own questions.
  7. G7 Data quality. Some writings carry wrong dates in the index ("Against the Arians c. AD 175–180"; "the Diatessaron 1st century BC – AD 70"); a wrong date the answer repeats fails restraint.
  8. G8 Reliability. The data worker failed under six concurrent asks (two of three passage reads), and its catalog was down for days until today; answers were written without the verse they were about.
  9. G9 Latency. 50–90 s against 12–19 s; most of it in gather, select and the revise round (44% of answers).
  10. G10 Measurement limits. One judge; the gold is not reviewed case by case; 80 questions guide design but do not prove a release; the reference answers are mostly one tradition (Reformed), so "covers the reference" rewards that tradition's framing.

9. Directions we see (not decided — improve on them)

  • A question-family taxonomy with typed plans. Classify into families (doctrine/catechism, verse meaning, word study, person/place, history of reading, comparison, pastoral, apologetic, factual) and build the plan from a library of typed, code-validated steps — e.g. doctrine: concept → proposition → proof texts → traditions' statements → reception; person: entity → kin and events → verses → writings naming them.
  • A doctrine layer the ask can query. Load the doctrine context (propositions, commitments, proof texts) into the ask's store, and extend it: for each common doctrinal question, the proposition, its proof texts and how major traditions state it — with care that evaluation questions are not answered from their own gold.
  • Skills with coverage checklists and examples. For each family, the points a complete answer covers and two or three exemplar answers; a code check that the outline covers the checklist.
  • A cross-reference channel. Make study-Bible-style cross-references a first-class ontology channel (verse → related verses with a reason), rather than relying on the classifier to name them.
  • Use the story layer and dossiers. Call verse_dossier for verse questions: referents, cast, the edition's notes, scroll copies — precomputed.
  • A fast path. For a simple doctrinal or factual question, a smaller plan (fewer channels, one model call) with the same verification.
  • Fix the measurement first where it lies. Exclude a question's own source from its evidence when grading; fix wrong dates at the index.

11. Questions for you

  1. Given G2 and G3, what should the ontology contain for the ask — and is a doctrine layer the right first addition, or a cross-reference graph, or a question-family plan library?
  2. Should the plan be built per question from typed steps (and validated by code), or should the fixed pipeline stay with better skills? If built, what is the step library?
  3. What should a skill artifact contain beyond instructions — checklists, exemplars, retrieval plans, tests?
  4. How should an answer serve readers of different traditions when the reference answers are mostly Reformed?
  5. How do we beat 12–19 s answers without giving up verification — a fast path, caching, precomputed dossiers, streaming?
  6. What would you measure to know each step worked, and in what order would you build it?
