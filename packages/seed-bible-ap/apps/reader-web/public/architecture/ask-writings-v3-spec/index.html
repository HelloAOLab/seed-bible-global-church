ask-writings v3: question-shaped answers over the ontology

Specification, for review. Date: 1 November 2026. Status: proposed. It answers the gaps in the planning brief: the ontology reaches 3% of what our answers cite, doctrine questions have nothing structured behind them, the skills are instructions only, and every question runs the same plan. v3 makes the question a typed object, compiles a plan for it from an operation library over the ontology, packages each skill with the plan, the points a complete answer must cover and worked examples, extends the ontology where answers need it, and measures everything with the answer's own sources held out.

1. Summary

  • Question frames. Classify stops naming one of nine kinds and fills a typed frame: the family, the subject (a passage, concept, doctrine, person, precept or practice — each an ontology node), the aspect asked, the answer form, the tradition scope. Code validates the frame with SHACL.
  • Plans compiled per question. A library of about twenty typed operations, each a query over the ontology or the writings, each an ep-plan:Step with typed inputs and outputs. A plan template per family is the default; the model may propose a different plan, and code accepts it only if it type-checks, fits the budget and contains the family's required operations.
  • Coverage points. Each family names the points a complete answer covers (a commandment question: what it requires, what it forbids, its ground, its fulfilment in the New Testament, its reach to the heart). Select plans the outline against them; code checks every required point is answered or explicitly said not to be held.
  • Skill packages. A skill becomes a package in the existing ase: ontology: voice and rules, frame bindings, plan template, coverage checklist, answer-form schema, reviewed exemplars, named graph queries, evaluation cases and a budget profile — compiled into the agent and checked by preflight.
  • An ontology that answers. Teaching facets for the 184 theological concepts; a loci layer, proof texts and tradition statements in the doctrine context; precepts with their duties and prohibitions; the 17,639 OpenBible cross-references (already in the ontology, never reached the ask) projected and typed; question exemplars. Extracted by Haiku, admitted by code, reviewed in priority order.
  • Honest measurement. Every fact carries its source; for each evaluation set, the sources its references were drawn from are quarantined from the evidence when it is graded.

2. Principles

  1. The ontology plans, the evidence proves. Graph facts decide what to look for and what a complete answer covers; the answer's claims still rest on held, verified text. A graph fact may itself be cited only where it is reference data, said as such.
  2. Models propose, code decides. Frames, plans, extracted facts and outlines are model-proposed and code-admitted (SHACL, type checks, verse validation, leakage checks).
  3. One harness. Families change the plan, never the system.
  4. Reuse before minting. New terms ground on the uppers (DOLCE/DnS, PROV-O, P-Plan/EP-Plan) and extend existing contexts (scr:, sdo:, ase:) before any new namespace.
  5. Every fact has a source and a review status. Proposed facts are usable, labelled, and reviewed in the order they most affect answers.

3. The flow

# Stage Input → output Who
1 Frame question → AskFrame (family, subject nodes, aspect, form, scope) Haiku proposes; SHACL + entity resolution decide
2 Plan frame + skill package → plan (DAG of operations with bound slots, budget) template, or Haiku proposal accepted by the type checker
3 Execute plan → evidence graph (items with provenance, the nodes they came through) code, in parallel waves
4 Coverage evidence graph × coverage points → gaps → re-plan (≤ 2 rounds) code
5 Outline asks + coverage points + evidence → outline, one entry per point Haiku; code checks every required point is covered or declared not held
6 Compose outline → answer in the family's form, claims tagged with evidence and graph nodes Haiku
7 Verify claims → struck / kept; leakage, dates, layers, coverage, form code (+ one revise)
8 Trace an EP-Plan execution bundle: frame, plan, steps, evidence, checks code

4. The question frame

A frame is a dul:Description of the asker's situation (DnS), stored with the run. Proposed terms (new context ask, prefix aqf:, grounded on the agentic-trust base):

Slot Values (C-box unless a node) Example ("What are the duties required in the seventh commandment?")
aqf:family QuestionFamily: doctrine · precept · verse-meaning · word-study · person-or-place · event · history-of-reading · comparison · source · collection · edition · pastoral · apologetic · factual precept
aqf:subject node(s): scr:Passage, scr:TheologicalConcept, sdo:DoctrineProposition, sdo:Locus, sdo:Precept, scr:Referent, a held work sdo:precept-decalogue-7 (Exod 20:14; Deut 5:18)
aqf:aspect AskAspect: meaning · definition · requirement · prohibition · ground · purpose · identity · history · comparison · application · evidence-for · objection requirement
aqf:answerForm AnswerForm: direct-statement · list · yes-no-with-reason · explanation · narrative · comparison · definition list
aqf:traditionScope TraditionScope: common-Christian · named-tradition · compare-traditions common-Christian (a named catechism → named-tradition)
aqf:depth Depth: brief · standard · study standard

A SHACL shape per family says which slots are required (a precept question needs a precept subject and an aspect). Subjects are resolved by code against the knowledge base and the doctrine layer (names, Strong's numbers, loci labels); an unresolved subject is recorded and the family's fallback plan runs.

5. The operation library

Each operation is an aqf:Operation ⊑ ep-plan:Step with typed input and output variables, a cost class and a latency class, and is implemented by an existing or new data-worker tool.

Operation In → out Backed by State
ResolvePassage reference → verses (verified) resolve, get_passage_text exists
VerseDossier verse → referents, cast, scene, notes, witnesses verse_dossier exists, unused
CrossReferences verse → related verses with relation and weight OpenBible (17,639 at ≥ 20 votes, CC BY), UBS parallels, TSK (public domain, to ingest) in the ontology, not projected
ConceptProfile concept → definition, key passages, related concepts, distinctions kb_concepts + teaching facets (§9.1) partial
DoctrineProfile proposition / locus → statement, proof texts, tradition statements, relations doctrine layer (§9.2) new projection
PreceptProfile precept → duties, prohibitions, proof texts, NT fulfilment precept model (§9.3) new
ConfessionalText tradition × locus → the held confession's article (by locator) writings_locate over Schaff and held creeds exists, unused for this
EntityProfile referent → facts, kin, events, verses kb_facts, get_entity, kb_verses_of partial
WordStudy Strong's → occurrences, senses, the edition's renderings lemma_occurrences, term senses partial
InterpretationOptions verse → open questions, candidate readings, paths get_chapter_interpretations exists, unused
Reception verse / proposition × period → dated writings citing it writings_at, chronology exists
Chronology proposition → when it enters the record, with sources reference chronology (143) new projection
MeaningSearch · LexicalSearch · LocateCited query → units per layer writings_retrieve, writings_lexical, writings_locate exists

6. The plan compiler

  • Templates. Each family's skill package carries a plan template (p-plan:Plan): e.g. precept = ResolvePassage → PreceptProfile → CrossReferences(precept passages) → ConfessionalText(tradition scope) → optional Reception; doctrine = DoctrineProfile → ConceptProfile → CrossReferences(proof texts) → ResolvePassage(proof texts) → ConfessionalText; verse-meaning = VerseDossier → CrossReferences → ConceptProfile(key terms) → InterpretationOptions (only if the verse has open questions) → Reception(depth = study).
  • Dynamic proposals. For a question that does not fit one family cleanly (a comparison inside a pastoral question), Haiku proposes a plan as a small JSON DAG over operation ids with bound slots. Code accepts it only if: every operation exists; every input variable is bound to a frame slot or an earlier output of the right type; it contains the family's required operations; it fits the budget profile. Otherwise the template runs. Both are recorded.
  • Budgets. brief (≤ 4 operations, one model call after framing), standard (≤ 10), study (≤ 16, with Reception). The asker's depth and the family set the profile.
  • Re-planning. After execution, uncovered coverage points (§7) map to operations that can fill them; at most two rounds; the stop reason is kept.
  • Trace. Frame, plan, each step's activity and outputs, and checks are written as an ep-plan:ExecutionTraceBundle, so a plan's failures are diagnosable by step.

7. Coverage points

A C-box of aqf:CoveragePoint values per family, each with a required flag, the operations that can supply it, and a test the outline must pass.

Family Coverage points (required in bold)
precept what it requires · what it forbids · its scriptural ground · its New Testament fulfilment · its reach to motive and heart
doctrine a direct statement · scriptural ground in both testaments where it exists · key distinctions (e.g. justification / sanctification) · where traditions differ (if they do) · its bearing on faith and life
verse-meaning the plain sense · the context · the key term(s) · the cross-reference that explains it · the open question, if the verse has one
pastoral speak to the person · what Scripture offers here · one concrete step · when to seek a pastor or professional
apologetic the objection stated fairly · the answer, with its evidence · what remains unresolved, honestly
history-of-reading the text · the earliest dated readings · the turning points · later readings as reception

8. Skill packages

A skill becomes an ase:SkillPackage (the agent-skills-engineering context already models packages, bundled resources, evaluations, cases and assertions). Contents:

Part What it is Checked by
SKILL.md voice and the family's rules (as today) lint
Frame binding the families and aspects it serves every family has exactly one skill
Plan template operations, slot bindings, budget profile type check against the operation library
Coverage checklist the family's coverage point ids ids exist in the C-box
Answer form a schema: e.g. a list form requires items, each with a passage compose output validated against it
Exemplars (2–3) reviewed question → outline → answer, from sources outside every evaluation set leakage check: no exemplar from a quarantined source; no eval question
Named queries the graph queries its operations run they exist on the data worker
Evaluation cases ase:EvalCase with assertions (coverage, form, restraint) run by the slice runner

Exported into the agent by the existing exporter, extended to compile the package; preflight refuses a package whose parts do not check.

9. Ontology extensions (T-box, C-box, A-box)

9.1 Concepts that teach (scr:)

Today's 184 scr:TheologicalConcepts carry rendering rules for translation. Add teaching facets: scr:teachingGloss (what the concept means, in two sentences), scr:keyPassage (concept → passage with a role: defining, illustrating, developing), scr:relatedConcept / skos:broader / skos:narrower, scr:Distinction (two concepts and the difference, e.g. justification / sanctification), scr:Misreading (a common confusion, stated). Coverage target: all 184 concepts plus the loci's core concepts.

9.2 Doctrine that answers (sdo:)

  • sdo:Locus (C-box): the systematic loci — God, Trinity, Scripture, creation, providence, sin, Christ's person and work, atonement, justification, sanctification, perseverance, Church, sacraments, last things, law and the Decalogue, prayer, worship — about 40 values; every sdo:DoctrineProposition placed in one or more.
  • sdo:ProofText: proposition → passage, with a role (primary, supporting, illustrative) and a basis (the text says it · a tradition reads it so).
  • sdo:TraditionStatement: tradition × proposition → affirms · denies · qualifies, with the held confessional text that says so (by locator in Schaff or the held creeds), never quoted from memory.
  • Today's 162 propositions are the register's — when a position enters the record. Add the propositions a teaching answer needs for the common questions in each locus (expected ~600).

9.3 Precepts (sdo:, extending scr:Command)

sdo:Precept (a standing command: the ten commandments, the great commandments, key New Testament imperatives) with sdo:Duty and sdo:Prohibition items, each with proof texts, and its fulfilment (e.g. Matt 5:27–28 for the seventh). Grounded on dul:Norm.

9.4 Cross-references

Project the 17,639 OpenBible pairs (≥ 20 votes) already in scripture.crossrefs.ttl to the runtime store; ingest the Treasury of Scripture Knowledge (public domain); type each pair by relation (quotes · alludes · parallels · explains · fulfils · contrasts) — by code where a source says so (UBS quotations), otherwise proposed by Haiku and labelled proposed.

9.5 Questions and answers as data

The frame vocabulary (§4), coverage points (§7) and exemplars (§8) live in the new ask context, so a family is added by data, not code.

9.6 Data quality

A date audit of the writings index (wrong dates found: "Against the Arians c. AD 175–180"; "the Diatessaron 1st century BC – AD 70"), with the chronology as the check.

10. The extraction run

The house pattern — Haiku proposes, code admits, a person reviews in priority order — over held, licence-cleared sources.

Target Sources Code admits only if Expected size
Concept teaching facets Scripture (the concept's Strong's occurrences), held Fathers and commentaries every key passage is a verse of the canon containing one of the concept's lemmas; no 6-word run of a held English Bible edition 184 concepts × ~5 facets
Loci and propositions held confessions (Schaff), creeds, Fathers; Scripture each proposition has ≥ 2 proof texts that resolve; placed in a locus; source locator resolves ~600 propositions
Tradition statements held confessions by tradition the locator resolves to a held unit that the statement paraphrases (similarity check), never invented ~600 × 4 traditions
Precepts Scripture, held expositions every duty or prohibition has a proof text that resolves ~40 precepts × ~10 items
Cross-reference typing OpenBible, TSK, UBS both ends resolve; relation from the source where it exists ~50k pairs
Exemplars questions outside every evaluation set leakage check; reviewer approval 2–3 per family

Every admitted fact carries prov:wasDerivedFrom (its source unit), prov:wasGeneratedBy (the run), and a review status. Cost: Haiku only, a few dollars per thousand facts; GraphDB is the reconstitutable store, D1 the runtime projection.

11. Verification

  • Coverage check (code): every required coverage point is an outline entry with evidence, or an explicit "not held" line.
  • Form check (code): the answer matches the family's form schema (a list has items, each with a passage).
  • Claim → node: each claim names the graph node it states (a proposition, a precept item, a concept facet); a claim that contradicts its node's reviewed statement is flagged.
  • Existing checks stay: evidence ids, layers, dates, quotations, claims about the evidence itself.

12. Runtime and latency

  • Every graph an operation reads is projected to D1 (the runtime store); GraphDB stays the source of record.
  • Precomputed dossiers: per verse (exists), per concept, per proposition, per precept — one read each.
  • The brief profile merges outline and compose into one call; plans run in parallel waves; the answer streams.
  • Target: brief questions under 20 s, standard under 45 s, with verification unchanged.

13. Evaluation and leakage quarantine

  • Quarantine. Each evaluation set names the sources its references came from (Reformation Study Bible notes for the study-note sets; the Westminster, Heidelberg, 1689, Baltimore and Beddome texts for the catechism sets; CREDO's sources). In evaluation, every operation drops evidence and graph facts derived from them (by provenance) for that set's questions. Measured today: 12 of 28 study-note answers cited their own reference note.
  • Gates on the 80-question slice, blind Haiku judge, quarantine on: addresses the question ≥ 0.88; covers the reference ≥ 0.65; restraint ≥ 0.92; Scripture support ≥ 0.90; strict good answer ≥ 0.40 — each above Apologist and Bonfire. Confirm on the 477-question suite before release.
  • Ablations: frames only; + plan library; + coverage; + doctrine layer; + skill packages — one tag per commit, run from a frozen worktree.

14. Phases and gates

Phase Build Gate
P0 Quarantine in the eval; re-baseline ours, Apologist, Bonfire honest numbers on the slice
P1 Frames + coverage points + form schemas for the six largest families; skill packages for them intent and coverage rise; nothing falls
P2 Operation library over existing tools (dossier, cross-references projected, interpretations, confessional text); plan templates; re-planning catechism coverage ≥ 0.5; latency not worse
P3 Extraction run: concept facets, loci, propositions, proof texts, tradition statements, precepts; review queue doctrine and precept families ≥ Apologist
P4 Dynamic plan proposals with type checking; brief profile; streaming all gates in §13; brief questions < 20 s
P5 Confirm on the 477 suite; deploy above both apps on every headline measure

15. Risks and open questions

  • Tradition. The references are mostly Reformed. Tradition statements let an answer state the common Christian reading and then each tradition's — but which framing leads by default, and for whom?
  • Graph as authority. A proposed doctrine fact must not be presented as what Scripture says. Claims still rest on held text; graph facts plan and check.
  • Extraction quality. Model-proposed doctrine is the riskiest data we would hold; admission rules and review order matter more than volume.
  • Over-planning. Dynamic plans can grow; budgets and type checks bound them, and the template is always the fallback.
  • Open: should frames be shown to the reader ("you asked what the seventh commandment requires")? Should the doctrine layer serve other surfaces (the Seed reader's Discover)?
